# Spec 07: High-Fidelity Sandbox Refactor

## Problem

Phase 3 runs HypoPG simulations inside `dblens-meta-db`. That metadata database does not contain the target application's schemas, table cardinalities, PostgreSQL statistics, extensions, constraints, or indexes. As a result, `EXPLAIN` cost estimates are based on synthetic local tables and can diverge sharply from the real production planner behavior.

## Architectural Shift

DB-Lens will move HypoPG simulation to the target database connection owned by the Python telemetry daemon.

The daemon already connects to the configured target database during each polling cycle to read `pg_stat_statements`. Phase 3.5 extends that same target-side connection to:

1. read high-impact statements from `pg_stat_statements`;
2. identify statements whose real target plan includes sequential scans;
3. infer a candidate index from simple table and predicate patterns;
4. execute `hypopg_create_index` on the target database;
5. compare `EXPLAIN (FORMAT JSON)` total cost before and after the hypothetical index;
6. persist the proposed SQL and estimated reduction into `MetricsHistory`.

The Node.js API no longer runs HypoPG. It only reads pre-calculated remediation fields from the metadata database and maps them into the existing response shape.

## Data Model

`MetricsHistory` gains two nullable fields:

- `proposedIndexSql`: the target-ready `CREATE INDEX` statement generated by the daemon.
- `costReductionPct`: the estimated planner cost reduction percentage measured on the target database with HypoPG.

Rows without a viable target-side simulation keep both fields `NULL`.

## Runtime Responsibilities

### Python telemetry daemon

- Owns target database access.
- Performs all target-sensitive SQL parsing and planning.
- Runs `EXPLAIN` and HypoPG on the same target where table statistics live.
- Stores remediation outputs alongside metric snapshots.
- Logs and skips remediation when HypoPG is unavailable or a query cannot be safely simulated.

### Node.js backend

- Serves metrics from `dblens-meta-db`.
- Applies lightweight rule flags for API compatibility.
- Builds `remediation` directly from `MetricsHistory.proposedIndexSql` and `MetricsHistory.costReductionPct`.
- Does not create sandbox tables, call HypoPG, or execute arbitrary query plans.

## Expected API Contract

When a metric has remediation data, the API returns:

```json
{
  "remediation": {
    "proposed_sql": "CREATE INDEX ...;",
    "estimated_cost_reduction_percentage": 91.25,
    "sandbox_note": "HypoPG estimate was calculated on the target database using target schema and statistics."
  }
}
```

The response remains backwards-compatible at the object level while removing locally fabricated cost fields.

## Operational Notes

- The target database must have HypoPG available to perform simulations.
- The daemon attempts `CREATE EXTENSION IF NOT EXISTS hypopg`; managed databases may require enabling the extension ahead of time.
- `EXPLAIN` is run without `ANALYZE`, so statements are planned but not executed.
- The first implementation intentionally supports conservative single-table candidate indexes. More complex joins, expressions, partial indexes, and multi-table candidates can be added after the target-side pipeline is stable.
